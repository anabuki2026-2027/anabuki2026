# プルリクエストの前のチェック

README「6. 毎日の作業の流れ」と、`docs/teams/README.md` の「リーダー・副リーダーの仕事」で確認する内容を、出す前に確かめる。

> **git のコマンドは、AI は実行しない**（`AGENTS.md`）。
> git の情報が必要なときは、使っている人に Git Bash で実行してもらい、結果を貼ってもらう。

## 1. git の情報をもらう

使っている人に、次のようにお願いする。

```text
Git Bash で、次の 3 行をまとめて貼り付けて Enter を押し、出てきた結果をここに貼ってください。

git branch --show-current
git status
git diff --stat
```

## 2. ブランチを確かめる

貼ってもらった 1 行目（ブランチ名）を見る。

- `main` や `teamB/main` のような**チームの main だったら、そこで止める。** README「② ブランチを作る」を案内する。
- ブランチ名が `teamX/名前-作業内容`（X はチームの大文字 1 文字）の形になっているか確かめる。`teamb/...` のように小文字になっていたら知らせる。
- 名前の先頭（`teamB` など）から、使っている人のチームがわかる。

## 3. 変更したファイルを確かめる

貼ってもらったファイルの一覧を見て、次のどれかがあれば知らせる。

- **自分のチームの担当ではないファイル**（ファイルの先頭コメントの【担当】、または `docs/FILES.md` の担当欄で確認する）
- `vendor/`、`tmp/`、`logs/`、`config/app_local.php`、名前が `.env` で始まるファイル
- 【担当】が「なし」や 🚫 のファイル
- 触った覚えのなさそうなファイル（使っている人に「これは変えましたか？」と聞く）

`.env` のファイルが一覧にあっても、**中身は絶対に見ない**。「このファイルはコミットしないでください」とだけ伝える。

B チームが Bake で作った `tests/` のファイルは、一緒に出してよい（`docs/teams/team-b.md` のとおり）。

新しく作ったファイルに先頭コメントがあるか、`docs/FILES.md` に追加されているかも確かめる（`AGENTS.md` の「ファイルの先頭コメント」）。

## 4. 自動チェックを動かす

これは git ではないので、AI が実行してよい。

```bash
composer check
```

GitHub の CI と同じ内容。エラーが出たら、どのファイルの何行目で、何がダメなのかを日本語で説明する。
書き方のエラーだけなら、`composer cs-fix` で自動で直せることを伝える（実行する前に聞く）。

## 5. 結果を伝える

```text
| チェック | 結果 |
| --- | --- |
| ブランチ | ✅ teamB/suzuki-users-model |
| 変更したファイル | ⚠️ templates/Users/add.php は C チームの担当です |
| 自動チェック | ✅ テスト・書き方チェックとも OK |
```

全部 OK なら、本人が Git Bash で実行するコマンド（`git add`、`git commit`、`git push`）を案内する。
プルリクエストの `base` は**自分のチームの main**（例：`teamB/main`）にすることも伝える。
