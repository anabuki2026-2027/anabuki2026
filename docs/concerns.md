# 公開後の懸念点

このアプリを公開したあとに困りそうなこと（懸念点）を、見つけるたびにここへ書き足していくファイルです。
完成したら先方に引きつぎ、そのあと約 1 か月半でイベントで使い、公開します。そのため、**引きつぎのときに先方へ伝えること**もここにまとめます。

- 新しい懸念点を見つけたら、一番下の「[書き足し方](#書き足し方)」の形で追加してください。
- 対応が終わっても消さずに、状態を「🟢 対応ずみ」に変えて残します（あとで「なぜこうしたか」が分かるように）。
- 管理は A チームが行います。ほかのチームの人が見つけたときは、A チームに伝えるか、プルリクエストで追加してください。

## くわしく

### C-01 PHP 8.2 のサポートが公開前に終わる

| 項目 | 内容 |
| --- | --- |
| 状態 | 🟡 対応中（プロジェクトは 8.4 に切りかえずみ。開発環境の Docker への移行待ち） |
| 重大度 | 高 |
| 見つけた日 | 2026-11-19 |
| 担当 | A |

**何が心配？**
PHP 8.2 は **2026/12/31 でサポートが終わり**、それ以降はセキュリティの修正が出ません。公開は 2027 年の予定なので、このままだとサポートが切れた PHP で公開することになります。

**対応**

- PHP 8.4 へ移行する。8.4 はセキュリティの修正が 2028/12/31 まで出る。Xserver では 8.3〜8.5 を選べるので、8.4 を選べる。
- 2026-11-20 に PHP 8.4.28 で試し、テスト・書き方チェック・トップページの表示がすべて問題なく動くことを確認した。
- 2026-11-25 に、`composer.json`（`require.php` と `config.platform.php`）・`composer.lock`・CI・`.vscode/settings.json`・README などの「8.2」を「8.4（8.4.28）」に書きかえた。開発チームには PHP 8.4.28 への入れかえを呼びかけている。
- 2026-11-25 に、開発環境を XAMPP から Docker に移すことにした（`docker-migration-plan.pdf`）。Docker の箱の PHP は `Dockerfile` で 8.4.28 に固定しているので、これからは全員の PHP の版が自動でそろう（1 人ずつ入れかえる必要がなくなる）。
- 残っている作業：全員の Docker への移行（12/1 まで）。12/9 まで予備として残す XAMPP の PHP は、そのあいだ XAMPP で作業する人だけ 8.4.28 に入れかえておく。

**先方へ伝えること**
公開サーバーの PHP は 8.4 を選ぶこと。8.4 のサポートは 2028/12/31 で終わること。

### C-02 手元と公開サーバーで DB の種類がちがう

| 項目 | 内容 |
| --- | --- |
| 状態 | 🟡 対応中（Docker で手元も MariaDB 10.11 にそろえる。全員の移行は 12/1 まで） |
| 重大度 | 高 |
| 見つけた日 | 2026-11-19 |
| 担当 | A・F |

**何が心配？**
（2026-11-19 時点）手元（XAMPP）は **MySQL 8.3**、Xserver のレンタルサーバーは **MariaDB 10.11** です（パネルの名前は「MySQL 設定」ですが、中身は MariaDB です）。
MySQL と MariaDB は似ていますが、まったく同じではありません。そのため、「手元では動くのに、公開すると動かない」ことが起きるおそれがあります。
また、手元の MySQL 8.3 はサポートが終わっていて、見つかった脆弱性（CVE-2026-114952）も直っていません。手元では `127.0.0.1` だけで待ち受けているので、すぐの危険は小さいです。

**対応**

- 先生から「開発環境は好きにしてよい」と返事をもらった。公開サーバーは、先生と先方が決めた Xserver（MariaDB 10.11）のまま。
- 2026-11-25 に、開発環境を Docker に移すことにした。Docker の箱の DB は `compose.yml` で **MariaDB 10.11**（Xserver と同じ）に固定している。試作で、MariaDB 10.11.19 で `bin/cake bake` と `bin/cake migrations migrate` が動くことを確認した。
- `config/Migrations/`・`config/Seeds/`・`src/Model/` はまだ空なので、今なら切りかえるだけで済む。
- テーブルは Migrations で作る（手で作らない）。F チームは MariaDB 10.11 で動く書き方にする。
- 全員が Docker に移って、XAMPP（MySQL）を使わなくなったら（12/9 のあと）、🟢 にする。

**先方へ伝えること**
使っている DB の種類と版。MariaDB 10.11 のサポートは 2028 年 2 月に終わること。

### C-03 公開サーバーでデバッグモードがオンのままになるおそれ

| 項目 | 内容 |
| --- | --- |
| 状態 | 🔴 未対応 |
| 重大度 | 高 |
| 見つけた日 | 2026-11-20 |
| 担当 | A |

**何が心配？**
`config/app_local.example.php` は、`DEBUG` が設定されていないとき、**デバッグモードをオンにする**作りになっています（14 行目の `env('DEBUG', true)`）。
公開サーバーの `config/app_local.php` をこの見本からコピーして作ると、デバッグモードがオンのまま公開されてしまいます。

**どうなる？**

- エラーが起きたとき、ファイルの場所・プログラムの中身・SQL が、見に来た人の画面に表示される。
- 画面の右下に DebugKit（開発用の道具）が出ることがある。
- 下の C-04 の、URL のチェックも動かなくなる。

**対応**

- 公開サーバーでは、必ず `DEBUG` を `false` にする。
- 公開する前に、わざとエラーを起こして、くわしい情報が表示されないことを確かめる。

**先方へ伝えること**
公開サーバーの `DEBUG` は `false` のままにすること。

### C-04 公開用の URL を設定しないとページが開けない

| 項目 | 内容 |
| --- | --- |
| 状態 | 🔴 未対応 |
| 重大度 | 高 |
| 見つけた日 | 2026-11-20 |
| 担当 | A |

**何が心配？**
`src/Middleware/HostHeaderMiddleware.php` は、デバッグモードがオフのとき、次のようにチェックします（36〜50 行目）。

- 公開用の URL（`APP_FULL_BASE_URL`）が設定されていない → **すべてのページがエラー（500）** になる。
- 開いた URL のドメインが、設定したドメインとちがう → **エラー（400）** になる。

このチェックは、ほかのサイトになりすました攻撃（Host ヘッダーインジェクション）を防ぐためのもので、外してはいけません。

**どうなる？**
公開した瞬間に、全部のページが開けないことがあります。`www` があるかないか、Xserver の初期ドメイン（`〇〇.xsrv.jp`）で開いたかどうか、でも 400 になります。

**対応**

- 公開するドメインが決まったら、`APP_FULL_BASE_URL` に設定する（例：`https://example.com`）。
- `www` の付く URL と付かない URL のどちらで公開するかを決め、もう片方は転送（リダイレクト）する。
- 公開する前に、決めた URL で開けることを確かめる。

**先方へ伝えること**
ドメインを変えるときは、`APP_FULL_BASE_URL` も変えること。

### C-05 公開サーバーの `SECURITY_SALT` を使い回すおそれ

| 項目 | 内容 |
| --- | --- |
| 状態 | 🔴 未対応 |
| 重大度 | 高 |
| 見つけた日 | 2026-11-20 |
| 担当 | A |

**何が心配？**
`SECURITY_SALT` は、暗号化などに使う「ひみつの文字列」です。
`.github/workflows/ci.yml` には、テスト用の値がそのまま書いてあり、GitHub で見られます。この値や、手元のパソコンの値を公開サーバーで使うと、暗号化の意味がなくなります。

**対応**

- 公開サーバー用に、新しい値を作る。
- その値は GitHub にも、このファイルにも書かない。

**先方へ伝えること**
`SECURITY_SALT` の値は先方だけで管理すること。外にもれたら新しい値に変えること（変えると、ログイン中の人は全員ログアウトされる）。

### C-06 引きついだあと、誰が更新するかが決まっていない

| 項目 | 内容 |
| --- | --- |
| 状態 | 🔴 未対応 |
| 重大度 | 中 |
| 見つけた日 | 2026-11-20 |
| 担当 | A（先方・先生と相談） |

**何が心配？**
公開したあとも、PHP・CakePHP・ライブラリには、セキュリティの修正が出つづけます。
今は、GitHub の Dependabot が「更新しませんか？」とプルリクエストを作ってくれます（`.github/dependabot.yml`）。しかし、引きついだあとにリポジトリの持ち主が変わったり、見る人がいなくなったりすると、この知らせを受け取る人がいなくなります。

**どうなる？**
脆弱性が見つかっても直されず、古いままで動きつづけることになります。

**対応**

- 引きつぎの前に、先方・先生と次のことを決める。
  - 公開したあと、更新するのは誰か（先方か、学校か、学生か）。
  - GitHub のリポジトリを誰が持つか。
  - いつまで運用するか（イベントが終わったら止めるのか、つづけるのか）。

**先方へ伝えること**
上で決めたこと。サポート期限（PHP 8.4 は 2028/12/31、MariaDB 10.11 は 2028 年 2 月）。

## 書き足し方

新しい懸念点は、次の形で「くわしく」の一番下に足して、上の「一覧」にも 1 行足してください。番号は `C-07`、`C-08` … と順番につけます。

```markdown
### C-07 （懸念点をひとことで）

| 項目 | 内容 |
| --- | --- |
| 状態 | 🔴 未対応 |
| 重大度 | 高・中・低のどれか |
| 見つけた日 | 2026-xx-xx |
| 担当 | 〇 チーム |

**何が心配？**
（何が問題か。根拠になるファイルと行の番号もあれば書く）

**どうなる？**
（放っておくと、公開後に何が起きるか）

**対応**
（どうするか。決まっていなければ「未定」と書く）

**先方へ伝えること**
（引きつぎで伝えることがあれば書く。なければ「なし」）
```

パスワードや `SECURITY_SALT` の値など、ひみつの情報はこのファイルに書かないでください。
